# Безопасность

Публикуйте только исходники. `.env`, каталог `data`, базы SQLite и сессии Telegram исключены из Git и Docker build context. Не добавляйте их принудительно. В репозитории нет общего Telegram API ID/API Hash: каждый владелец получает собственные реквизиты и вводит их в своей форме после развёртывания.

Перед публикацией выполните `npm run scan` и `gitleaks git --redact --no-banner .`. После публикации склонируйте репозиторий в новую папку и повторите обе проверки. Встроенная проверка ищет подозрительные файлы, реквизиты и персональные ссылки во всех Git-объектах; Gitleaks дополняет её собственными правилами. Проверка секретов не доказывает отсутствие всех уязвимостей приложения.

Доступ на сервере защищает случайный ключ владельца длиной 256 бит. Браузер получает HttpOnly-cookie; POST-запросы панели требуют точный Origin. MCP использует отдельные OAuth-токены с ограниченным сроком. Коды OAuth одноразовые, проверяются PKCE и адрес ресурса. На Sites identity-заголовки доверены только в режиме `DEPLOY_TARGET=sites` и сравниваются с настроенным владельцем. Node-сервер принудительно использует режим server и удаляет входящие identity-заголовки.

Telegram API Hash и сессия шифруются AES-256-GCM. Коды входа и пароль 2FA не сохраняются. Сервер получает их на время HTTPS-запроса и передаёт SDK. Администратор хостинга с доступом к ключу и данным способен восстановить сессию, поэтому разворачивайте экземпляр на своём сервере или в своём Sites.

Исполнитель даёт владельцу полный SDK и исходящие HTTP-запросы. Подключённая модель способна выполнять порученные изменения в Telegram. Это одноарендная установка; не открывайте доступ другим пользователям и не превращайте её в публичный сервис исполнения кода без отдельного проектирования изоляции.

Не публикуйте секреты в Issues. При подозрении на утечку сначала отзовите Telegram-сессию в списке устройств, затем смените ключ владельца и OAuth-доступ.
